# 제출 전 체크리스트 답변

## 1. MemberService에서 `@Transactional`을 사용한 이유

`MemberService`는 "여러 SQL을 하나의 작업 단위로 묶는 책임"을 지는 계층이라고 판단해, Repository가 아니라 Service에 `@Transactional`을 붙였습니다.

| 메서드 | 실행하는 SQL | `@Transactional`이 필요한 이유 |
|---|---|---|
| `insertMember` | INSERT 1건 | SQL은 1건뿐이지만, 서비스 계층의 트랜잭션 경계를 통일해 두면 이후 검증/부가 로직이 추가돼도 자동으로 같은 트랜잭션에 편입됩니다. |
| `payMember` | BILLING INSERT + BOWLER.STATUS UPDATE (2건) | 두 SQL이 하나로 묶이지 않으면, 예외 발생 시 "정산 내역은 쌓였는데 상태는 그대로"이거나 반대로 "상태만 바뀌고 정산 내역이 없는" 데이터 불일치가 생길 수 있습니다. `@Transactional`로 묶어 예외 시 전체 롤백되도록 했습니다. |
| `deleteMember` | DELETE 1건 (CASCADE로 BILLING도 삭제) | 삭제 도중 예외가 발생했을 때도 일관되게 롤백을 보장하기 위해 사용했습니다. |
| `resetAll` | BOWLER 삭제 + 시퀀스 2개 초기화 (3건) | 하나라도 실패하면 "데이터는 지워졌는데 시퀀스는 이전 값 그대로"인 상태가 남을 수 있어, 전부 성공하거나 전부 롤백되도록 묶었습니다. |
| `getActiveList`, `getSalesReport` | SELECT | 데이터 변경이 없으므로 `@Transactional(readOnly = true)`를 사용해 실수로 조회 메서드 안에서 쓰기 작업이 들어가는 것을 방지하는 안전장치로 활용했습니다. |

핵심 요약: **정산 처리(payMember)와 전체 리셋(resetAll)처럼 SQL이 2건 이상 실행되는 로직에서 원자성(all-or-nothing)을 보장**하기 위해 사용했고, 단일 SQL 메서드에도 서비스 계층 트랜잭션 경계를 일관되게 유지하기 위해 동일하게 적용했습니다.

## 2. 프로젝트 변경 사항

### MyBatis 적용 (기존: JDBC(JdbcTemplate)만 적용)

- `pom.xml`에 `mybatis-spring-boot-starter` 의존성을 추가했습니다.
- `com.kh.bowling.mapper.MemberMapper` 인터페이스(`@Mapper`)와 `src/main/resources/mapper/MemberMapper.xml`을 새로 작성해, 기존에 `MemberRepository`가 `JdbcTemplate`으로 직접 실행하던 SQL을 MyBatis Mapper XML로 옮겼습니다.
- `MemberRepository`는 더 이상 `JdbcTemplate`을 사용하지 않고 `MemberMapper`를 주입받아 위임하는 방식으로 변경했습니다.
- `application.properties`에 `mybatis.mapper-locations`, `mybatis.configuration.map-underscore-to-camel-case=true`를 추가해 `BOWLER_ID` 같은 DB 컬럼명이 `bowlerId` 같은 자바 필드명으로 자동 매핑되도록 설정했습니다.
- 리셋(`resetAll`)처럼 SQL 3건이 순차 실행되는 로직은 Mapper 메서드 3개(`deleteAllBowlers`, `resetBowlerSequence`, `resetBillingSequence`)로 나누어 정의하고, Service의 `@Transactional`이 이 3건을 하나의 트랜잭션으로 묶도록 구성했습니다.

### Lombok 적용 (기존: dependency만 추가, 실사용 없음)

- `pom.xml`에 `lombok` 의존성을 `optional=true`로 추가했습니다.
- `MemberDTO`, `BillingDTO`의 수동 getter/setter를 제거하고 `@Getter`, `@Setter`, `@NoArgsConstructor`를 적용했습니다.
- 필드 일부만 초기화하는 커스텀 생성자(예: `MemberDTO(name, laneNumber, gameCount, grade)`, `BillingDTO(bowlerId, totalFee)`)는 전체 필드를 요구하는 `@AllArgsConstructor`로 대체할 수 없어 그대로 유지했습니다.
